# SmartTrip Batam - Sistem Rekomendasi Itinerary Design

Date: 2026-09-07
Team: 6 orang, 1 semester
Deliverable: Aplikasi (Laravel REST API + Flutter mobile). Laporan akademik di luar scope dokumen ini.

## 1. Problem Statement

Wisatawan Batam kesulitan menentukan destinasi wisata/kuliner yang cocok dengan minat, lokasi, waktu, dan anggaran mereka, serta menyusun rute perjalanan yang efisien. SmartTrip membantu user menemukan tempat yang sesuai preferensi dan menyusun jadwal perjalanan (itinerary) otomatis.

## 2. Architecture Overview

**Backend: Laravel, REST API only, auth via Laravel Sanctum (API token mode - opaque bearer token, bukan JWT; dipilih karena first-party, gampang di-revoke, cukup buat skala project ini). Dua cara masuk: email/password, atau Google Sign-In - keduanya berakhir dengan Sanctum token yang sama, cuma beda cara verifikasi identitas awal. Database: PostgreSQL (bukan MySQL default Laravel yang biasa dipakai tim - keputusan sadar). Hosting: Linux server, dipakai sama buat development dan deployment.**

- `places` sync module - Artisan command (`php artisan places:sync`), dijalankan manual (admin trigger) atau terjadwal ringan (bulanan), menarik data tempat wisata/kuliner/hotel Batam dari Google Places API (New) ke tabel `places` lokal. Upsert idempotent berdasarkan `google_place_id`.
- `recommendation` module - hitung bobot kriteria dari input slider user, scoring TOPSIS terhadap kandidat tempat, clustering K-Means untuk pembagian hari, nearest-neighbor routing per hari.
- `itinerary` module - simpan itinerary (hanya untuk user yang login), swap item, tracking source (wishlist vs recommended), read-only sharing trip ke user lain via `trip_viewers` (Section 9).
- `admin` module - CRUD places (termasuk field kurasi admin), CRUD categories, review place_candidates (discovery/approve/reject), dashboard analitik - **web panel Blade + Bootstrap terpisah** (Section 14), bukan bagian dari app Flutter. Diputuskan ulang: admin side balik ke web, bukan mobile lagi.

**Admin Panel: web terpisah (Laravel Blade + Bootstrap), bukan bagian dari app Flutter.**

- Admin login lewat halaman web biasa (`/admin/login`), pakai session auth standar Laravel (guard `web`) - **bukan** Sanctum bearer token yang dipakai Flutter. Dua sistem auth terpisah buat dua client yang beda: Flutter (mobile, Sanctum token) buat user biasa, web Blade (session) buat admin.
- Controller Blade panggil Eloquent model langsung (pola yang sama seperti project Laravel tim lainnya - business logic di controller, tanpa service layer) - **bukan** panggil endpoint `/api/admin/*` dari sisi server sendiri. Endpoint `/api/admin/*` yang sempat didesain buat Flutter admin screens sekarang tidak diperlukan lagi (lihat Section 12 - dihapus dari daftar endpoint).
- `users.role` (`user`/`admin`) tetap dipakai buat bedain siapa yang boleh akses `/admin/*` - middleware biasa, bukan role-gate di UI Flutter.

**Mobile: Flutter - cuma buat user biasa (wisatawan), admin tidak pernah buka app ini.**

- **Login/register wajib sebelum bisa bikin trip** - tidak ada alur guest lagi (diputuskan ulang, disederhanakan dari desain awal). Browse katalog tempat (`GET /api/places`) tetap bisa tanpa login, tapi begitu masuk ke "Buat Trip" langsung diarahkan ke login/register kalau belum. Ini menghilangkan kebutuhan guest trip token, endpoint "save/attach trip", dan logic auth kondisional - trip selalu langsung terikat ke `users_id` sejak dibuat.
- Semua komunikasi ke backend lewat REST + Sanctum bearer token. Tidak ada panggilan langsung ke Google API dari mobile (API key tetap di server) - kecuali `google_maps_flutter` (render peta) dan `geolocator` (lokasi GPS device), yang keduanya tidak butuh API key berbayar/panggilan server sama sekali.
- Foto tempat **tidak** di-hotlink langsung ke Google - Google Places Photo (New) butuh API key di URL buat ambil bytes gambar, jadi kalau mobile fetch langsung, key ke-expose ke client. Sync menyimpan foto ke storage lokal server (sesuai konvensi tim: file disimpan lokal, bukan cloud storage), `photo_url`/`place_photos.photo_url` menunjuk ke path server sendiri.
- UI bilingual (ID/EN) lewat Flutter i18n standar (`easy_localization` atau `intl` bawaan) - murni client-side, tidak ada endpoint tambahan.
- Notifikasi (reminder mulai hari, notif mendekati stop berikutnya, notif window forecast cuaca terbuka - Section 11) pakai `flutter_local_notifications` - **dijadwalkan/dipicu murni di device**, bukan push server. Reminder mulai hari dijadwalkan client-side begitu itinerary di-generate (pakai `daily_start_time` + tanggal hari itu); notif mendekati stop numpang di event geofence entry yang sama dengan visit-tracking (Section 8); notif forecast dijadwalkan client-side ke `start_date - 7 hari` begitu itinerary di-generate (Section 11). Tidak butuh Firebase Cloud Messaging atau endpoint backend baru - berlaku juga buat fitur trip viewer (Section 9), yang juga sengaja tanpa push.

**Kenapa split begini:** panggilan Google Places (yang berbayar/quota-limited) selalu lewat server dan batched, bukan per user mobile. Scoring TOPSIS juga selalu terhadap data lokal, jadi cepat dan tidak bergantung latency API eksternal.

## 3. Feasibility Check (Google Places API, peta, routing)

- **Field coverage:** cukup. Google Places API (New) punya `displayName`, `location` (lat/lng), `types`/`primaryType` (attraction/restaurant subtypes/lodging), `rating`, `userRatingCount`, `priceLevel`, `regularOpeningHours`/`currentOpeningHours`, `photos`.
- **Pricing (Places):** kredit blanket $200/bulan sudah tidak berlaku (expired Feb 2025). Model sekarang: free calls per SKU per bulan - Nearby/Text Search (Pro SKU) 5.000 panggilan gratis/bulan, Place Details dengan field rating+jam buka+harga (Enterprise SKU) hanya **1.000 panggilan gratis/bulan**.
- **Implikasi:** batasi jumlah tempat awal (~300-500 tempat lintas kategori attraction/culinary/lodging di Batam) supaya full sync awal tetap dalam kuota gratis. Sync tetap manual/admin-triggered (tombol "sync now"), bukan cron agresif harian, supaya tidak boros kuota Enterprise. Akun Google Cloud baru juga dapat trial credit $300 sekali pakai yang cukup menutupi testing satu semester.
- **Peta & rute jalan (kenapa Google, bukan TomTom):** Maps SDK for Android/iOS (dipakai lewat `google_maps_flutter`) gratis tanpa batas untuk render peta - jadi tidak ada biaya tambahan buat nampilin peta itu sendiri. Rute jalan asli (turn-by-turn, ngikutin jalan) pakai Google Routes API (`computeRoutes`), masuk tier Essentials dengan 10.000 panggilan gratis/bulan - jauh lebih dari cukup karena API ini cuma dipanggil sekali per hari-itinerary saat generate atau swap (bukan per view). TomTom punya free tier lebih besar (2.500 req/hari) tapi tidak ada Flutter SDK resmi, jadi butuh effort tambahan buat integrasi tile peta sendiri tanpa manfaat jelas dibanding Google yang sudah gratis. Lokasi user saat ini tidak butuh API sama sekali - cukup `geolocator` (akses GPS device langsung).
- **Catatan operasional:** Google Maps Platform tetap butuh billing account (kartu kredit) aktif walau memakai kuota gratis - perlu disiapkan salah satu anggota tim.
- **Revisi 2026-10-13 - peta & rute pindah dari Google:** billing project Google tidak bisa diaktifkan (free trial minta prepayment), jadi render peta pindah ke `flutter_map` + tile OpenStreetMap (tanpa API key; kebijakan tile OSM mewajibkan User-Agent dan atribusi, cukup untuk skala demo) dan rute jalan pindah ke OpenRouteService (`driving-car`, paket Standard gratis 2.000 request/hari tanpa kartu kredit). Rute tetap satu call per hari-itinerary; OpenRouteService mengembalikan satu geometri utuh plus indeks tiap waypoint (`way_points`), lalu backend memotongnya per leg dan menyimpannya sebagai encoded polyline format Google, jadi `polyline_to_here` dan decoder di mobile tidak berubah. Google Places (discovery/details/foto) belum diganti; selama billing belum aktif, katalog lokal diisi `PlaceSeeder` (31 tempat nyata Batam, nama & koordinat dari OpenStreetMap). Paragraf di atas tentang Maps SDK/Routes API dibiarkan sebagai catatan keputusan awal.
- **Revisi 2026-10-13 (lanjutan) - data tempat pindah ke Geoapify:** billing Google tetap tidak bisa diaktifkan, jadi Discovery dan Place Details memakai Geoapify (berbasis OpenStreetMap, gratis 3.000 kredit/hari tanpa kartu kredit). Geoapify mencari di dalam lingkaran, bukan nama area, jadi tiap kecamatan diwakili titik tengah + radius kira-kira (`PlaceDiscoveryService::AREAS`). Alur dua fase tetap: Discovery -> review admin -> approve (Place Details + Gemini). Yang hilang dibanding Google: rating (tetap null, ditangani `PlaceRatingEstimator` dan ulasan in-app) dan foto (diisi admin). `places.source` bertambah nilai `geoapify`; kolom `google_place_id` di `places` dan `place_candidates` di-rename jadi `external_place_id` (migration `2026_10_13_000002`, unique index ikut di-rename) karena sekarang berisi place_id Geoapify. Model Gemini default jadi `gemini-flash-lite-latest` (sekitar 3,5 detik per enrichment, sedangkan `gemini-flash-latest` timeout 60 detik di tiap retry). Kuota di dashboard (F024) jadi kredit Geoapify hari ini. Paragraf Google Places di atas dibiarkan sebagai catatan keputusan awal.
- **Revisi 2026-10-13 (dedup) - kunci tempat jadi elemen OpenStreetMap:** `place_id` Geoapify ternyata bukan kunci stabil (isinya koordinat + ID OSM + nama, jadi hasil search dan details untuk tempat yang sama beda ID, dan berubah kalau node OSM digeser). `external_place_id` sekarang berisi elemen OSM (`osm:n123`/`osm:w123`/`osm:r123`, dari `datasource.raw`), Place Details diambil pakai `osm_type`/`osm_id`, dan tempat seed dapat ID dari kolom OSM di `PlaceSeeder`. Ditambah dedup nama + jarak (lihat langkah 1a).
- **Revisi 2026-10-13 (wishlist pribadi) - wishlist level user, terpisah dari wishlist per trip:** mockup Figma punya tab Wishlist di bottom nav, layar "B3. Daftar Wishlist" dan badge "N Favorit" di katalog home (B1), dan tombol hati di kartu katalog harus jalan tanpa trip apapun yang dipilih. Sebelumnya satu-satunya wishlist adalah `trip_wishlist_places` (wajib `trips_id`), jadi ditambah pivot `user_wishlist_place` (migration `2026_10_13_000003`, lihat Section 4) plus `GET`/`POST /api/wishlist` dan `DELETE /api/wishlist/{place}` (Section 12). `trip_wishlist_places` dan `/api/trips/{id}/wishlist` tidak berubah dan tetap jadi input generate; rencananya di langkah C2 user memilih dari wishlist pribadi (plus custom pin) untuk trip itu - integrasi C2 ini belum dibangun (C2 masih stub). Test: `UserWishlistTest` (7 test, total backend 319 lulus).
- **Revisi 2026-10-13 (deskripsi AI) - Gemini menulis deskripsi kalau sumber kosong:** Geoapify dan tempat seed tidak punya deskripsi, jadi call Gemini yang sama (Section 5) sekarang juga menulis deskripsi singkat Bahasa Indonesia 2-3 kalimat yang netral (dilarang mengarang harga, jam buka, nomor telepon, atau fasilitas yang tidak pasti) lalu menerjemahkannya ke `description_en`. Disimpan di `places.description` (slot sumber), bukan `description_override` milik admin. Enrichment hanya mengisi field kosong dan tidak menimpa yang sudah dikonfirmasi admin (`category_tags_reviewed`); hotel dapat deskripsi tapi tidak dapat tag minat dan durasi kunjungan. Apa pun yang diisi Gemini mengembalikan `category_tags_reviewed` ke false, sehingga tempat muncul di dashboard sebagai "hasil AI (deskripsi/tag) belum direview" sampai admin menyimpan form edit-nya. Logika ini dipakai bersama oleh approve kandidat dan perintah baru `php artisan places:enrich` untuk tempat yang sudah ada di katalog (`PlaceEnrichmentService`).
- **Urutan bootstrap - `categories` diseed duluan:** tagging AI (langkah 4 di bawah) cuma boleh pilih dari `categories` yang sudah ada (Section 5) - kalau tabelnya masih kosong, tidak ada yang bisa disarankan. Jadi urutannya: seed `categories` dengan taksonomi awal (~10-15 tag baku via Laravel seeder, admin bisa tambah/edit belakangan) **sebelum** proses places bootstrap di bawah dijalankan.
- **Bootstrap data awal - kenapa tidak cukup 1 kali panggil sync:** Nearby/Text Search cuma balikin maks 20 hasil per call (60 dengan pagination), walau radius di-set sampai 50km - jadi 1 search tidak akan pernah nyampe 300-500 tempat, cuma dapat "yang paling menonjol" berulang-ulang. Solusinya sync jalan dalam **2 fase**:
  1. **Discovery (murah, Pro SKU):** jalankan Nearby/Text Search per kombinasi area x kategori (misal per kecamatan di Batam x attraction/culinary/lodging, sekitar belasan area x 3 kategori) - hasilnya (name, lokasi, tipe dasar, external_place_id) masuk tabel staging `place_candidates`, BUKAN langsung ke `places`. Fase ini murah karena cuma butuh field dasar (Pro SKU), tidak menyentuh kuota Enterprise yang ketat. **1 kali trigger sudah loop semua kombinasi area x kategori** - bukan 1 API call, tapi 1 operasi bootstrap yang cukup buat nyampe target awal (~300-500 tempat) sekali jalan, dengan asumsi Batam memang punya sebanyak itu tempat.
  1a. **Idempotensi - kenapa re-trigger Discovery tidak dobel data:** admin bisa trigger Discovery lagi kapan saja (nambah area baru, atau cek tempat baru yang muncul di Google belakangan) - tiap `external_place_id` hasil pencarian dicek dulu terhadap **`places` DAN `place_candidates` (status apapun, termasuk `rejected`)** sebelum di-insert. Kalau sudah ada di salah satu (baik sudah jadi place resmi, masih pending, atau sudah pernah ditolak), dilewati - tidak insert ulang. Ini penting khusus buat status `rejected`: tanpa cek ini, tempat yang sudah sengaja ditolak admin bakal terus muncul lagi tiap kali Discovery di-re-run, bikin review jadi berulang-ulang buat hal yang sama. **Selain ID (sejak 2026-10-13):** hasil dengan ID beda atau tanpa ID tetap dianggap sama kalau namanya saling memuat sebagai kata utuh ("Ocarina" vs "Pantai Ocarina") dan jaraknya maksimal 100 m (`PlaceDuplicateFinder`), karena tempat seed/manual tidak selalu punya ID dan OSM sering memetakan satu tempat dua kali (node pintu masuk + way gedung). Cabang dengan nama sama yang lebih jauh dari 100 m tetap masuk. Approve juga menolak kandidat yang sudah ada di katalog sebelum memakai kredit Geoapify, dan `php artisan places:reject-duplicates` menolak kandidat pending yang duplikat tempat atau kandidat sebelumnya.
  2. **Review admin:** panel nampilin daftar candidate hasil discovery (bisa ratusan/ribuan, termasuk noise kayak warung kecil yang ke-tag "restaurant"), admin pilih/approve mana yang layak jadi `places` beneran.
  3. **Enrichment (mahal, Enterprise SKU, cuma buat yang di-approve):** candidate yang di-approve baru di-fetch Place Details lengkap (rating, jam buka, harga, foto, deskripsi) dan dipromosikan ke `places` - di sinilah kuota 1.000/bulan kepake, jadi dijaga cuma buat tempat yang beneran lolos review, bukan semua hasil discovery mentah. `place_candidates.search_area` ikut disalin jadi `places.kecamatan` di langkah promosi ini (revisi 2026-09-22) - gratis, Discovery memang sudah jalan per-kecamatan, admin tinggal koreksi kalau meleset.
  4. **Tagging (langsung nyambung ke akhir Enrichment):** begitu `description` tersimpan dari Place Details, satu call Gemini (Section 5) langsung jalan buat tempat itu - hasilnya `description_en` (auto-translate) dan `category_tags` (disarankan dari daftar `categories` yang ada, `category_tags_reviewed = false`). Jadi tiap tempat yang lolos approve otomatis lengkap (foto, deskripsi 2 bahasa, tag kategori) tanpa langkah manual terpisah - tag-nya cuma nunggu direview admin (sudah bisa dipakai algoritma dari awal, lihat Section 5).
  5. Proses ini dijalankan sekali di awal buat isi data awal (~300-500 tempat), lalu admin bisa ulang discovery kapan saja buat nambah area/kategori baru.
- **Bilingual & kuota:** sync dari Google cuma sekali per tempat dalam satu bahasa (Indonesia) - fetch ulang dalam Bahasa Inggris buat tiap tempat akan menggandakan pemakaian kuota Enterprise (sudah ketat di 1.000/bulan). Konten Inggris (`description_en`) **bukan** ditulis manual oleh admin - begitu `description` (ID) tersedia (dari Google atau admin override), backend auto-translate ke Inggris pakai Gemini API (lihat Section 5 - satu provider AI buat translasi & tagging kategori sekaligus). Hasil auto-translate tetap disimpan sebagai field yang bisa di-override admin kalau hasilnya kurang pas, bukan dikunci permanen.
- **Kenapa Gemini buat fitur AI (translasi & tagging kategori):** Gemini API (model Flash/Flash-Lite) benar-benar gratis terus-menerus tanpa kartu kredit, cuma dibatasi rate limit (5-15 request/menit, sampai 1.000 request/hari) - beda dari OpenAI/Claude yang cuma kasih kredit trial sekali pakai (~$5, ada masa berlaku) baru bayar per-token setelahnya. Cocok banget buat kebutuhan proyek kuliah yang volume-nya kecil (300-500 tempat) tapi butuh AI yang genuinely gratis jangka panjang.
- **Cuaca (Open-Meteo, Section 11):** gratis tanpa API key sama sekali buat pemakaian non-komersial, forecast sampai 16 hari ke depan, cakupan global berbasis model atmosfer (bukan whitelist lokasi) jadi koordinat Batam otomatis kesupport. Karena tidak butuh key, dipanggil **langsung dari Flutter client-side** (bukan lewat backend) - konsisten sama alasan `google_maps_flutter`/`geolocator` di Section 2 (API tanpa key tidak perlu diproksi lewat server).

## 4. Data Model

- **`places`** *(digabung dari `places` + `place_attributes` sebelumnya - keputusan direvisi 2026-09-22, lihat catatan proteksi di bawah)* - places_id (PK), external_place_id (nullable, unique - elemen OpenStreetMap di balik hasil Geoapify, format `osm:n123`/`osm:w123`/`osm:r123`, dulu `google_place_id`, BUKAN referensi ke `places_id` kita, lihat catatan penamaan di akhir Section 4), name, type (`attraction`/`culinary`/`lodging`), lat, lng, address, kecamatan (varchar, nullable - revisi 2026-09-22, lihat catatan asal data di bawah), opening_hours (json), photo_url (thumbnail utama, path lokal server - lihat Section 2), description (nullable, dari Google `editorialSummary`, Bahasa Indonesia - tidak semua tempat punya), business_status (`operational`/`closed_temporarily`/`closed_permanently`, default `operational` - sync mengecualikan yang `closed_permanently` dari rekomendasi), types (json, raw Google types array buat label kategori lebih detail di layar), source (`google`/`manual`), category_tags_reviewed (bool, default false - ditandai true begitu admin cek hasil tagging AI), estimated_visit_minutes (diisi AI - Gemini nebak durasi kunjungan wajar berdasar tipe/kategori tempat, misal museum ~90 menit, cafe ~45 menit - bagian dari call enrichment yang sama di Section 5, admin bisa override), is_outdoor (bool, diisi AI - Gemini nebak apakah tempat ini sensitif cuaca/kegiatan luar ruangan, misal pantai/taman = true, mall/museum/kebanyakan kuliner = false - dipakai buat saran swap cuaca di Section 11, admin bisa override), estimated_cost_idr (nullable, admin manual - prioritas utama buat kriteria anggaran, lihat Section 7), description_override (nullable, Bahasa Indonesia), description_en (nullable, auto-translate via Gemini API saat data ID tersimpan, admin bisa override hasilnya - fallback ke `description`/`description_override` kalau tetap kosong saat UI dalam mode EN), timestamps, **deleted_at (soft delete, revisi 2026-09-22 - lihat catatan kebijakan hapus di bawah)**
  - **Kategori tempat BUKAN kolom JSON lagi** (direvisi 2026-09-22, sebelumnya `category_tags` json array) - pindah ke tabel pivot `place_category` (lihat di bawah `categories`), supaya referential integrity ke `categories.categories_id` beneran ditegakkan oleh database, bukan cuma asumsi di kode.
  - **`kecamatan` baru (revisi 2026-09-22):** diisi otomatis dari `place_candidates.search_area` pas candidate dipromosikan (Discovery memang sudah jalan per-kecamatan, jadi datanya gratis - tidak butuh reverse-geocoding/API tambahan). Admin bisa koreksi manual kalau meleset (misal pencarian dipusatkan di satu kecamatan tapi hasilnya ada di kecamatan tetangga karena posisinya dekat perbatasan). Dipakai buat filter kecamatan di layar browse tempat (`GET /api/places?kecamatan=...`).
  - **`search_keywords` baru (revisi 2026-10-16):** text nullable, kata kunci pencarian per tempat dipisah koma (misal `snorkeling, pasir putih, sunset`). Katalog `GET /api/places?search=` mencocokkan nama ATAU kolom ini, jadi wisatawan yang mengetik "snorkeling" menemukan tempat yang memang punya kegiatan itu walau katanya tidak ada di nama. Diisi Gemini saat enrichment kalau masih kosong (Section 5), admin bisa ubah di Edit Tempat (dengan tombol "Sarankan dengan AI"). Sempat ditaruh di `categories` (2026-10-16 pagi) lalu dipindah ke sini: kata kunci satu kategori tidak cocok untuk semua tempat di dalamnya (kategori Pantai berisi juga restoran seafood tepi pantai), jadi nilai lama di kategori tidak disalin ke tempat.
  - **`google_maps_uri` DIHAPUS dari skema (revisi 2026-09-22, sebelumnya ada):** tidak perlu disimpan - link "Buka di Google Maps" dibangun on-the-fly di kode (`https://www.google.com/maps/search/?api=1&query={lat},{lng}`, cukup dari koordinat), bukan field tersimpan dari hasil sync Google. Alasan: satu kolom lebih sedikit yang perlu diproteksi whitelist-update, dan link yang dibangun selalu ikut `lat`/`lng` terbaru (kalau admin pernah koreksi koordinat, link lama yang tersimpan dari sync pertama bakal diam-diam nunjuk ke lokasi salah).
  - **Proteksi kode wajib terhadap kolom kurasi admin (`category_tags_reviewed`, `estimated_visit_minutes`, `is_outdoor`, `estimated_cost_idr`, `description_override`, `description_en`, `kecamatan`, plus baris `place_category` milik place ini):** sekarang satu tabel `places` dengan field yang di-refresh dari Google, jadi tanggung jawab menjaga field kurasi ini **pindah dari skema ke disiplin kode**. Job `places:sync`/re-sync WAJIB update pakai whitelist kolom eksplisit (Eloquent `->update([...])` dengan daftar kolom Google-only) - **tidak boleh** pakai `updateOrCreate()`/mass-assign dengan payload penuh dari Google, karena itu bakal menimpa balik semua kolom kurasi admin ke null/default tiap kali sync ulang jalan. Sync job juga tidak boleh menyentuh tabel `place_category` sama sekali (itu murni domain kurasi admin/AI, bukan data Google). Field promosi dari `place_candidates` (approve + enrichment pertama kali) boleh isi penuh karena itu insert baris baru, bukan update baris existing.
  - **Kebijakan hapus (revisi 2026-09-22):** `places` pakai **soft delete** (`deleted_at`), bukan hard delete. Alasan: admin sering "hapus tempat yang ternyata salah" sebagai aksi rutin pas kurasi data, tapi kalau tempat itu sudah pernah muncul di itinerary user (`itinerary_items.places_id`), hard delete bakal bikin FK constraint gagal (kalau RESTRICT) atau diam-diam ngerusak riwayat trip user (kalau CASCADE). Soft delete: tempat hilang dari hasil rekomendasi/browse (query utama selalu filter `deleted_at IS NULL`), tapi riwayat trip lama tetap utuh nunjukin tempat yang beneran dikunjungi user.
- **`categories`** - categories_id (PK), name_id (label Bahasa Indonesia - akhiran `_id` di sini kode bahasa ISO, BUKAN primary/foreign key), name_en, slug (unique, PARTIAL index `WHERE deleted_at IS NULL` supaya slug kategori yang sudah soft-deleted bisa dipakai ulang - jaga konsistensi, cegah duplikat mirip kayak "kuliner" vs "wisata kuliner"), timestamps, **deleted_at (soft delete)**. **Aturan unique + soft delete (ditambah 2026-10-04, ditemukan saat implementasi backend):** UNIQUE constraint biasa di tabel yang punya `deleted_at` ikut menghitung baris yang sudah soft-deleted, jadi baris baru dengan nilai sama langsung bentrok dengan baris lama yang cuma "disembunyikan". Aturannya per kasus, bukan blanket:
- **Wajib PARTIAL unique index (`CREATE UNIQUE INDEX ... WHERE deleted_at IS NULL`)** kalau nilai itu memang harus bisa dipakai ulang setelah soft delete. Sudah diterapkan di `place_reviews (users_id, places_id)` (user hapus review sendiri lalu review ulang tempat yang sama) dan `categories.slug` (admin hapus kategori lalu bikin lagi dengan slug sama). Postgres dan SQLite (dipakai test suite) sama-sama mendukung partial index, jadi tidak perlu guard per driver.
- **Tetap UNIQUE biasa dengan sengaja** di `places.external_place_id`: tempat yang sudah soft-deleted admin TIDAK boleh muncul lagi lewat Discovery. Pengecekan idempotensi Discovery (Section 3, langkah 1a) harus pakai `withTrashed()` supaya tempat yang dihapus tetap dianggap "sudah ada". Implementasi sudah begini (`PlaceDiscoveryService`).
- **Diputuskan 2026-10-04:** `users.email` dan `users.google_id` juga dijadikan PARTIAL unique index (`WHERE deleted_at IS NULL`), sama seperti `place_reviews`, sehingga email akun yang sudah soft-deleted (dinonaktifkan) bisa dipakai daftar ulang sebagai akun baru. Konsekuensinya: akun lama dan akun baru bisa punya email yang sama sebagai dua baris, jadi SEMUA pencarian user berdasarkan email atau `google_id` (login, verifikasi registrasi, lookup `POST /api/auth/google` di atas, undang viewer by email) wajib mengabaikan baris soft-deleted. Model `User` sudah memakai `SoftDeletes`, jadi query Eloquent biasa otomatis aman; yang perlu dijaga adalah raw query dan `withTrashed()`. **Status implementasi:** sudah diterapkan lewat migration `2026_10_04_000000_make_users_unique_indexes_ignore_soft_deletes` (didukung Postgres dan SQLite) dan diuji di `AuthTest` (email/google_id akun soft-deleted bisa dipakai ulang, dua akun aktif tidak boleh kembar). Belum ada fitur nonaktifkan akun, jadi aturan ini belum terpicu di praktik.
- Tabel pivot (`place_category`, `trip_interest_category`, `user_default_interest_category`, `trip_viewers`) tidak kena masalah ini karena tidak punya `deleted_at` (hard delete).
- **Relasi riwayat wajib `withTrashed()` (ditambah 2026-10-10, ditemukan saat audit):** tujuan `places.deleted_at` adalah itinerary lama tetap menampilkan tempatnya, tapi `Place` punya global scope `SoftDeletes` sehingga `$item->place` jadi NULL begitu tempat dihapus. Sekarang `ItineraryItem::place()`, `ItineraryDay::startPlace()/endPlace()`, `Trip::hotelPlace()`, dan `TripWishlistPlace::place()` dideklarasikan `->withTrashed()`. Semua jalur yang MEMILIH tempat (katalog, pool kandidat TOPSIS, swap candidates, hotel options, validasi wishlist/hotel) tetap pakai scope default jadi tidak pernah menawarkan tempat yang sudah dihapus; `ItineraryGenerator` juga melewati baris wishlist yang tempatnya sudah soft-deleted.
- **Unique baru 2026-10-10 (sebelumnya cuma invariant di kode):** `trip_wishlist_places(trips_id, places_id)`, `itinerary_days(trips_id, day_number)`, `itinerary_items(itinerary_days_id, places_id)`, `place_photos(places_id, sort_order)` - migration `2026_10_10_000000_add_missing_unique_constraints`.
- **Kebijakan FK `ON DELETE` yang terpasang** (hanya relevan untuk `forceDelete`, karena parent-nya soft delete): CASCADE dari `trips` ke `itinerary_days`/`trip_interest_category`/`trip_wishlist_places`/`trip_viewers`, dari `itinerary_days` ke `itinerary_items`, dari `places` ke `place_photos`/`place_reviews`/`trip_wishlist_places`, dari `users` ke `trips`/`place_reviews`/`trip_viewers`/`user_default_interest_category`; RESTRICT dari `categories` ke 3 pivot dan dari `places` ke `place_category`/`itinerary_items`/`itinerary_days.start|end_places_id`; SET NULL dari `places` ke `trips.hotel_places_id` dan dari `itinerary_items` ke `place_reviews.itinerary_items_id`. Karena generate ulang menghapus `itinerary_days` lama, review pasca-kunjungan kehilangan tautan `itinerary_items_id`-nya (review-nya sendiri tetap ada) - diterima sebagai konsekuensi desain.

**Konvensi penamaan primary/foreign key (revisi 2026-09-22):** semua primary key sekarang eksplisit `{nama_tabel}_id`, bukan `id` generik - `places_id`, `categories_id`, `users_id`, `trips_id`, `itinerary_days_id`, `itinerary_items_id`, `place_reviews_id`, `place_photos_id`, `place_candidates_id`, `trip_wishlist_places_id`, `trip_viewers_id` - supaya nama kolom langsung kebaca tabel apa yang dirujuk walau dilihat lepas dari konteks JOIN (mis. `trips.users_id` langsung jelas "trip ini merujuk ke sebuah baris `users`"). Foreign key generik ikut nama primary key yang dirujuk: `place_id` -> `places_id`, `category_id` -> `categories_id`, `user_id` -> `users_id`, `trip_id` -> `trips_id`, `itinerary_day_id` -> `itinerary_days_id`, `itinerary_item_id` -> `itinerary_items_id`. FK yang punya peran spesifik (bukan sekadar "yang mana") tetap pakai prefix peran, cuma bagian nama tabelnya ikut berubah: `hotel_place_id` -> `hotel_places_id`, `start_place_id`/`end_place_id` -> `start_places_id`/`end_places_id`. **3 pengecualian sengaja TIDAK ikut berubah:** (1) `external_place_id` (bernama `google_place_id` sampai 2026-10-13) dan `google_id` - itu ID eksternal milik penyedia, bukan referensi ke `places_id`/`users_id` kita, sekadar mirip nama secara kebetulan; (2) kolom `id`/`subject_id`/`causer_id` di tabel `activity_log` - dikontrol penuh oleh migration bawaan package `spatie/laravel-activitylog`, mengubahnya butuh publish+edit migration package sendiri, di luar scope revisi penamaan ini; (3) parameter `{id}` di URL route API (Section 12) - itu konvensi resource identifier REST di path URL, bukan nama kolom database, jadi tidak ikut berubah (walau field di body request yang memang mengisi kolom FK, seperti `place_id` di body `POST /api/trips/{id}/wishlist`, tetap disamakan jadi `places_id`).

## 5. AI-Assisted Data Enrichment (bukan scraping)

AI (Gemini API, lihat Section 3) dipakai buat memproses data yang sudah legal kita punya, bukan buat mengambil data baru dari situs pihak ketiga (lihat Section 16 - scraping tetap di luar scope, ganti "scraper" jadi "AI agent" tidak menghilangkan masalah ToS-nya):

- **Deskripsi awal:** Google Place Details punya field `generativeSummary`/`reviewSummary` (AI-generated summary dari review Google sendiri) - diminta langsung saat sync, jadi deskripsi berkualitas tanpa kerja tambahan, sudah termasuk dalam field yang dibayar/di-request dari Places API.
- **Translasi EN + tagging kategori + estimasi durasi kunjungan + is_outdoor - digabung jadi satu panggilan Gemini per tempat:** begitu `description` (ID) tersimpan, backend kirim satu request ke Gemini berisi name + types + description + daftar `categories` yang ada, minta output terstruktur (JSON) berisi (a) terjemahan Inggris, (b) kategori yang cocok **dari daftar yang sudah ada saja** (tidak boleh bikin tag baru sendiri - jaga taksonomi tetap rapi), (c) estimasi `estimated_visit_minutes` yang wajar berdasarkan tipe/kategori tempat, dan (d) `is_outdoor` (true/false, dipakai buat saran swap cuaca - Section 11). Satu call buat 4 kebutuhan sekaligus, bukan empat call terpisah - tetap jauh di bawah kuota rate-limit harian Gemini.
- **Kategori hasil AI tetap butuh review admin** (beda dari translasi yang cuma teks tampilan) - karena `category_tags` langsung dipakai di scoring TOPSIS (Jaccard similarity, Section 7), tag yang salah bisa bikin rekomendasi melenceng, bukan cuma typo kosmetik. `places.category_tags_reviewed` (bool, default false) ditandai true begitu admin cek/konfirmasi di panel - tag AI tetap langsung aktif dipakai algoritma sementara menunggu direview (tidak memblokir), tapi dashboard admin (Section 14) nampilin daftar "tempat yang kategorinya belum direview" biar tidak kelupaan selamanya.
- **Kata kunci pencarian (revisi 2026-10-16):** panggilan Gemini yang sama juga mengembalikan 6-10 kata kunci pencarian singkat untuk tempat itu (kegiatan, suasana, makanan, ciri khas). Disimpan ke `places.search_keywords` HANYA kalau kolom itu masih kosong - kata kunci yang ditulis admin tidak pernah ditimpa, dan seperti estimasi biaya, tidak membuka ulang review tag. Tempat tanpa kata kunci dianggap masih perlu enrichment (`places:enrich` mengisinya). Di halaman Edit Tempat ada tombol "Sarankan dengan AI" (`GET /admin/places/{place}/keyword-suggestions`) yang minta saran dari nama, kecamatan, kategori, dan deskripsi tempat; admin edit dulu sebelum Simpan. Daftar kategori yang dikirim ke Gemini untuk tagging berformat `slug (nama)`.
- **Volume & rate limit:** ~300-500 tempat x 1 call = 300-500 request, dijalankan sebagai background job setelah sync dengan jeda antar-request (respect 5-15 RPM limit Gemini free tier) - selesai dalam hitungan puluhan menit, jauh di bawah kuota 1.000 request/hari.

## 6. Rating Blend (Google + In-App)

Rating in-app dipakai buat blend dengan rating Google di kriteria TOPSIS, bukan cuma data analitik pasif. Supaya tempat baru dengan 1 review 5 bintang tidak mengalahkan tempat dengan 2.000 review asli, dipakai Bayesian-average blend (mirip formula rating IMDB): rata-rata in-app menarik bobot makin besar seiring bertambahnya jumlah review in-app, tapi hampir sepenuhnya mengikuti rating Google kalau review in-app masih sedikit/nol (menghindari cold-start problem).

## 7. Recommendation Engine Flow

1. **Trip setup (mobile):** num_days, budget_total (**per orang** - label di UI harus jelas "budget per orang", bukan total buat rombongan; tidak ada input jumlah orang di flow ini), start_date, daily_start_time/daily_end_time (optional, default 09:00-19:00), toggle "sudah punya hotel?".
2. **Wishlist (mobile, opsional):** user browse/scroll katalog tempat (seperti e-commerce - grid/list, filter kategori, infinite scroll via pagination) dan tambah ke wishlist. Ini terjadi sebelum tahap generate. Tombol hati di kartu katalog menyimpan ke wishlist pribadi (`user_wishlist_place`, revisi 2026-10-13) tanpa perlu trip, dan nantinya langkah C2 membiarkan user memilih dari wishlist pribadi itu ke `trip_wishlist_places` untuk trip yang sedang disusun (direncanakan, belum dibangun).
3. **Minat + bobot kriteria (mobile):** dua hal terpisah, jangan tertukar. (a) **Pilih minat** - multi-select chip dari daftar `categories` (alam, kuliner seafood, sejarah, dst) -> disimpan sebagai baris-baris di `trip_interest_category`, ini yang jadi ISI buat Jaccard similarity di langkah 5. (b) **Bobot kriteria** - user isi 4 slider (0-10): kesesuaian kategori/minat, jarak/lokasi, kesesuaian anggaran, rating/popularitas, nentuin seberapa PENTING tiap kriteria (termasuk seberapa penting kecocokan minat yang baru dipilih di atas). Backend normalisasi: `weight_i = rating_i / sum(semua rating)`.
4. **Hotel (backend):** kalau tidak punya hotel sendiri (input via search di katalog `places` atau custom pin lat/lng, sama seperti pola wishlist - Section 4), jalankan TOPSIS 3-kriteria (jarak ke area wisata terpilih, kesesuaian anggaran, rating) khusus `type=lodging`, tampilkan top-3 buat dipilih user. Bobot 3 kriteria ini **pakai ulang** 3 dari 4 kolom `weight_*` milik trip (jarak/anggaran/rating dari slider user, kategori/minat dibuang lalu sisanya dinormalisasi ulang supaya total tetap 1) - bukan skema bobot terpisah. "Area wisata terpilih" buat kriteria jarak dihitung dari centroid koordinat `trip_wishlist_places`; kalau wishlist kosong (user skip wishlist sama sekali), fallback ke centroid tempat kandidat berskor tertinggi di kategori minat yang dipilih user. Kalau sudah punya hotel, lewati langkah ini - lokasi yang diinput user jadi titik awal/akhir.
5. **Scoring kandidat (backend):** filter `attraction`/`culinary` berdasarkan kategori + kompatibilitas jam buka terhadap daily_start_time/daily_end_time, bangun matriks keputusan TOPSIS (baris = kandidat tempat, kolom = 4 kriteria dengan bobot dari langkah 3), hitung closeness-to-ideal score. Detail tiap kriteria:
   - **Kesesuaian kategori/minat** (benefit, maksimalkan) - Jaccard similarity antara set `categories_id` dari `trip_interest_category` milik trip ini (langkah 3a) dan set `categories_id` dari `place_category` milik tempat tsb.
   - **Jarak/lokasi** (cost, minimalkan) - Haversine dari hotel/titik awal.
   - **Kesesuaian anggaran** (cost, minimalkan) - dibandingkan terhadap `trips.budget_total` yang **per orang**; semua nilai biaya tempat (`estimated_cost_idr`, fallback default) juga diasumsikan basis per-kepala, jadi perbandingannya konsisten tanpa perlu tahu jumlah orang di rombongan. Nilai diambil berjenjang 3 tingkat (revisi 2026-10-18: tingkat `price_level` Google dihapus, Geoapify tidak punya data harga): (1) `places.estimated_cost_idr` kalau admin atau Gemini sudah isi, (2) kalau kosong, median harga tempat lain di kategori `type` yang sama yang datanya ada (imputasi netral - tempat tidak dihukum atau diuntungkan, cuma jadi rata-rata di kriteria ini), (3) **kalau kategori itu sama sekali belum ada satupun data harga** (bisa kejadian pas bootstrap awal - misal semua attraction belum ada input admin, jadi tidak ada apa-apa buat dihitung median-nya) - fallback ke nilai default hardcode per `type` (misal Rp 50.000 buat attraction/culinary, Rp 300.000 buat lodging) sampai data asli mulai terisi. Tetap dibedakan penuh oleh 3 kriteria lain di semua tingkat fallback ini.
   - **Rating/popularitas** (benefit, maksimalkan) - rata-rata ulasan in-app (revisi 2026-10-18: blend Bayesian dengan rating Google di Section 6 tidak dipakai lagi karena Geoapify tidak punya rating, `places.rating` dihapus). **Fallback 3 tingkat (ditambah 2026-10-10, `PlaceRatingEstimator`):** (1) rata-rata ulasan kalau tempat punya ulasan in-app, (2) kalau belum ada ulasan, median rating tempat lain di `type` yang sama di pool kandidat, (3) kalau pool-nya juga tidak punya data, nilai netral 3.5 - tempat tidak dihukum maupun diuntungkan, sama prinsipnya dengan tingkat 2-3 kriteria anggaran. Sebelumnya NULL diam-diam jadi 0.0 dan tempat manual tanpa review selalu kalah di kriteria ini.
6. **Pembagian hari (backend):**
   a. K-Means clustering (k = num_days) atas koordinat tempat wishlist, supaya wishlist yang lokasinya berjauhan tidak masuk hari yang sama.
   b. **Budget waktu per hari dihitung dari visit duration + estimasi waktu tempuh, bukan visit duration doang** - `sum(visit duration semua stop) + sum(estimasi waktu tempuh antar stop berurutan)` dibandingkan ke (`daily_end_time` - `daily_start_time`). **Visit duration per stop (revisi 2026-09-22):** `places.estimated_visit_minutes` kalau stop-nya dari katalog (wishlist katalog atau rekomendasi TOPSIS), **atau** `trip_wishlist_places.custom_visit_minutes` kalau stop-nya wishlist custom pin (tidak punya baris `places` sama sekali, jadi tidak ada `estimated_visit_minutes` buat diambil - lihat Section 4). Estimasi waktu tempuh: jarak Haversine **dikali faktor detour ~1.3-1.4x** (garis lurus meremehkan jarak jalan asli, apalagi di Batam yang berbentuk pulau dengan jembatan/garis pantai tidak beraturan - bukan grid kota biasa), baru dibagi asumsi kecepatan rata-rata kota ~25-30 km/jam. Ini cuma estimasi kasar buat keputusan muat/tidak muat di tahap ini - waktu tempuh asli dari Routes API baru diketahui di langkah 6e (setelah urutan fix), lihat validasi pasca-6e di bawah. Kalau total estimasi di satu cluster hari melebihi budget, item overflow (prioritas terendah - terjauh dari centroid cluster) otomatis didorong (push) ke hari berikutnya, cascading kalau perlu. Kalau tetap tidak muat sampai hari terakhir, hari itu dikembalikan dengan flag "tidak muat".
   c. Slot kosong tiap hari diisi tempat rekomendasi TOPSIS terdekat dari centroid cluster hari itu (atau dari hotel kalau hari itu tidak ada wishlist), berhenti nambah begitu proyeksi visit+tempuh (langkah 6b) bakal lewat budget hari itu. Tempat yang sudah dipakai di hari manapun dalam generate run yang sama langsung dikeluarkan dari pool kandidat hari berikutnya - tidak ada tempat yang muncul dobel di lebih dari satu hari.
   d. Nearest-neighbor (Haversine) dijalankan per hari (wishlist + recommended digabung) mulai dan berakhir di hotel/titik awal, untuk menentukan urutan kunjungan.
   e. Setelah urutan per hari fix, backend panggil API routing (OpenRouteService `driving-car` sejak 2026-10-13, sebelumnya Google Routes API `computeRoutes`) sekali per hari dengan seluruh waypoint (hotel -> stop 1 -> stop 2 -> ... -> hotel), lalu simpan tiap segmen ke `polyline_to_here` milik stop tujuan masing-masing (bukan satu polyline gabungan) - satu API call tetap cukup buat seluruh hari karena API routing mendukung multi-waypoint dalam satu request.
   f. **Validasi pasca-fakta:** bandingkan total durasi asli dari API routing (langkah 6e) + visit duration terhadap budget waktu hari itu. Kalau ternyata melebihi cukup jauh (estimasi kasar di 6b meleset), hari itu ditandai flag "padat" di response (sama seperti flag "tidak muat" di 6b) - bukan dibiarkan diam-diam jadi jadwal yang secara fisik terlalu padat.
7. **Swap (backend):** ganti satu item - ambil alternatif TOPSIS peringkat berikutnya yang belum dipakai (kategori & radius hari yang sama), atau user cari manual lewat browse/search penuh. Setelah swap, urutan NN dihitung ulang untuk hari itu (langkah 6d) dan `polyline_to_here` di-refresh buat stop yang urutannya berubah (langkah 6e) - hari lain tidak terpengaruh. **`topsis_score` item baru (revisi 2026-09-22, tadinya kelewat didokumentasikan):** kalau dari alternatif ranking, `topsis_score`-nya udah diketahui dari matriks scoring yang sama pas generate - tinggal disimpan. Kalau dari cari manual, `topsis_score` sengaja **dibiarkan NULL** - tempat itu memang tidak pernah discoring terhadap bobot trip ini, jadi maksa angka di situ cuma bikin data yang menyesatkan. NULL di sini artinya "dipilih manual", bukan data hilang.

Pipeline: **K-Means (pembagian hari)** -> **Weighted-TOPSIS (ranking kandidat)** -> **Nearest-Neighbor (urutan rute)** -> **OpenRouteService (polyline jalan asli per segmen)**.

## 8. Live Trip Map & Visit Tracking

Saat user membuka peta untuk hari yang sedang aktif, tampilan menunjukkan progres perjalanan hari itu, bukan cuma rute statis:

- **Marker hotel/titik awal** - dari `trips.hotel_places_id`, atau dari `trips.hotel_lat`/`hotel_lng` untuk hotel custom pin
- **Marker lokasi user saat ini** - live, dari `geolocator` position stream selama layar peta terbuka
- **Pin bernomor tiap stop** sesuai `visit_order`
- **Polyline per segmen** (`itinerary_items.polyline_to_here`) diwarnai **abu-abu** kalau stop tujuan segmen itu sudah `visited_at` terisi, **biru** kalau belum - persis pola warna rute yang sudah/belum dilalui di Google Maps navigasi
- **Titik akhir** - hotel yang sama

**Deteksi kunjungan (otomatis, geofencing):** selama trip berlangsung, mobile app mendaftarkan geofence radius 100m (default, bisa disesuaikan) untuk tiap stop yang belum `visited_at` di hari aktif, pakai plugin geofencing native (misal `geofence_service`) - bukan polling GPS manual, supaya lebih hemat baterai dan tetap jalan walau app di-background. Begitu geofence entry event terpicu, app memanggil `POST /api/itinerary-items/{id}/visit` untuk set `visited_at`, lalu peta refresh warna segmen terkait.

**Catatan risiko/scope:** location tracking background butuh permission "Allow all the time" di Android dan "Always" di iOS - keduanya permission sensitif yang direview ketat oleh Play Store/App Store dan wajib ada privacy policy kalau mau publish ke store. Untuk keperluan demo/skripsi (sideload/internal testing) ini bukan blocker, tapi kalau rencananya publish ke Play Store perlu effort tambahan (justifikasi permission, privacy policy) di luar todo teknis biasa. Server tidak (dan tidak perlu) memverifikasi keaslian lokasi device saat menerima `visit` - cukup untuk kebutuhan visualisasi progres, bukan sistem check-in yang butuh anti-fraud.

**Edge cases:**

- **Permission lokasi background ditolak, atau geofence tidak kepicu (GPS drift, radius meleset, user lewat tanpa masuk radius):** tiap stop tetap punya opsi **tandai manual** (long-press pin di peta, atau tombol di kartu itinerary) yang manggil endpoint `visit` yang sama - auto-detection jadi cara utama, bukan satu-satunya cara. Tombol yang sama juga bisa dipakai buat batalkan tanda (toggle, set `visited_at` balik ke null) kalau auto-detection salah trigger.
- **Stop yang di-skip** (user langsung ke stop 3 tanpa geofence stop 2 kepicu): segmen ke stop 2 tetap **biru selamanya** sampai user tandai manual - tidak ada auto-assume "kalau stop sesudahnya visited berarti ini juga visited", karena skip beneran (bukan cuma GPS meleset) itu valid use-case (misal user memang berubah rencana).
- **App ditutup penuh (bukan cuma di-background):** geofence didaftarkan di level OS (Android Geofencing API / iOS region monitoring via `geofence_service`), bukan terikat lifecycle layar peta - registrasi terjadi sekali saat user tap "Mulai Hari Ini" di awal hari itu, sehingga tetap bisa trigger & wake app walau app sudah di-kill, selama OS tidak mematikan proses sepenuhnya (lihat catatan battery optimization di bawah).
- **Tidak ada koneksi internet saat geofence trigger:** event `visit` disimpan dulu di local queue (SQLite/shared prefs), retry otomatis dengan backoff begitu koneksi kembali - bukan langsung gagal silent.
- **Trip multi-hari:** geofence cuma didaftarkan untuk stop-stop di hari yang lagi aktif (hari yang di-"Mulai"-kan), bukan seluruh hari sekaligus - supaya lewat dekat lokasi hari ke-3 saat masih hari ke-1 tidak salah ke-trigger. Geofence hari sebelumnya di-deregister saat pindah/mulai hari berikutnya.
- **Battery optimization (Android):** beberapa OEM (MIUI, OnePlus, dll) agresif mematikan background service walau geofence terdaftar di level OS - app perlu minta exemption dari battery optimization saat user pertama kali mulai live tracking, dan ini didokumentasikan sebagai known risk, bukan sesuatu yang bisa 100% dijamin dari sisi app.

**Akses read-only oleh user lain (bukan pemilik trip)** - lihat Section 9.

## 9. Trip Viewer (Read-Only Sharing)

**Ditambahkan 2026-09-23** - bukan future work, langsung masuk scope semester ini (revisi dari keputusan "kolaborasi antar user di luar scope" di Section 16). **Beda dari "Share Itinerary" di Section 10** - fitur ini butuh akun/login dan kasih akses viewer yang persisten + bisa dicabut per-orang; Section 10 anon, sekali lihat, tanpa akun sama sekali. Dua mekanisme terpisah, tidak saling gantiin. Pemilik trip (`trips.users_id`) bisa mengundang user lain (harus sudah terdaftar) buat **melihat** trip-nya - detail, itinerary per hari, status ("padat"/"tidak muat"), dan progres kunjungan live (pin abu-abu/biru sesuai `visited_at`, persis yang dilihat pemilik di Section 8) - **tanpa** bisa mengubah apapun.

- **Data model:** tabel baru `trip_viewers` (trip_viewers_id PK, trips_id FK, users_id FK - user yang diundang, added_at timestamp, unique(trips_id, users_id)) - pivot murni, additive, `trips.users_id` (pemilik) sama sekali tidak berubah. Lihat Section 4.
- **Cara undang - 2 jalur (revisi 2026-09-23, jalur link ditambah):**
  1. **Cari by email** (jalur awal) - pemilik cari user terdaftar by email di layar "Bagikan Trip" (Section 13), langsung ditambahkan ke `trip_viewers`. Cuma jalan kalau orangnya sudah punya akun.
  2. **Link undangan** (jalur baru) - `trips.viewer_invite_token` (varchar, nullable, unique - kolom baru, beda dari `share_token` di Section 10, JANGAN disamakan) di-generate pemilik dari layar "Bagikan Trip", dibagikan lewat share sheet OS (`smarttrip://invite/{viewer_invite_token}`). Penerima tap link -> **kalau belum login, diarahkan register/login dulu** (beda dari Section 10 yang anon) -> begitu berhasil auth, `POST /api/trips/join-viewer/{viewer_invite_token}` otomatis nambah baris `trip_viewers` buat user itu -> langsung masuk ke trip. Ini nutup celah jalur 1 (cari by email cuma jalan buat user yang SUDAH terdaftar) - link bisa dikirim ke siapa saja, mereka daftar dulu kalau belum punya akun, baru otomatis jadi viewer.
  - **Kedua jalur berakhir di tabel `trip_viewers` yang sama** - tidak ada sistem otorisasi kedua yang perlu dijaga konsisten, endpoint baca/tulis yang sudah ada di bawah tetap berlaku sama persis buat viewer manapun asalnya.
  - **Tidak ada langkah accept/reject** dari pihak yang diundang (kedua jalur) - karena risiko akses read-only rendah.
  - **Cabut/regenerate `viewer_invite_token` cuma menutup jalur MASUK BARU** - viewer yang sudah lebih dulu join lewat link lama tetap punya akses (baris `trip_viewers`-nya tidak tersentuh), sama persis seperti `share_token` di Section 10. Revoke per-orang tetap lewat hapus baris `trip_viewers` spesifik orang itu di layar "Bagikan Trip", terlepas dia join lewat email atau link.
  - **Catatan keamanan:** beda dari jalur email (pemilik tahu persis siapa yang diundang), link bisa diteruskan ke orang lain di luar niat pemilik - risikonya dibatasi karena (a) tetap butuh akun/login, (b) langsung kelihatan di daftar viewer layar "Bagikan Trip" begitu seseorang join, pemilik bisa cabut kapan saja kalau ada yang tidak dikenal.
- **Tidak ada notifikasi push ke user yang diundang** - konsisten sama prinsip aplikasi ini yang sengaja tanpa Firebase/backend push di semua fitur lain (Section 2). User yang diundang baru tahu dia dapat akses lewat tab baru **"Dibagikan ke Saya"** di app (Section 13) - dicek manual tiap buka tab itu, bukan real-time push.
- **Yang bisa dilihat viewer:** persis sama data yang dilihat pemilik - detail trip, itinerary per hari (Section 7), peta live + progres kunjungan (Section 8).
- **Yang TIDAK bisa dilakukan viewer** (ditegakkan di backend, bukan cuma disembunyikan di UI): generate/regenerate itinerary, swap tempat, hapus trip, tandai kunjungan manual, ubah wishlist/hotel/bobot preferensi. Semua endpoint tulis (write) tetap exclusive milik pemilik.
- **Enforcement:** endpoint baca yang sudah ada (`GET /api/trips/{id}` dan turunannya - wishlist, itinerary) diperluas otorisasinya dari "harus pemilik" jadi "pemilik ATAU ada baris `trip_viewers` buat user+trip ini" (Section 12). Endpoint tulis tidak disentuh sama sekali - tetap cek `trips.users_id === auth user` seperti sekarang, tidak ada perubahan di situ.
- **"Live tracking" viewer artinya polling state yang sama, BUKAN broadcast GPS pemilik:** viewer melihat progres lewat `visited_at` per stop yang sudah tersimpan di database (sama seperti pemilik lihat progresnya sendiri lewat refresh/poll) - **bukan** posisi GPS pemilik yang bergerak real-time di peta. Ini penting dijaga: lokasi GPS pemilik **tidak pernah dikirim ke server** (keputusan privasi yang sudah ada sejak awal, Section 8) - kalau nanti pemilik ingin viewer melihat titik GPS-nya bergerak real-time, itu butuh perubahan arsitektur baru (pemilik broadcast lokasi ke server + viewer subscribe), bukan bagian dari fitur read-only ini.
- **Hapus akses:** pemilik bisa cabut akses viewer kapan saja dari layar "Bagikan Trip" (hapus baris `trip_viewers`) - viewer langsung kehilangan akses ke trip itu.

## 10. Share Itinerary (Anonymous Public Link)

**Ditambahkan 2026-09-23** - fitur terpisah dan **tidak berhubungan** dengan Trip Viewer (Section 9), user eksplisit minta dua sistem beda. Tujuannya beda: bagikan **snapshot itinerary yang sudah digenerate** ke siapa saja lewat link, **tanpa perlu akun/login sama sekali** - cocok buat kirim ke orang yang belum tentu pakai app SmartTrip. Trade-off sadar: karena benar-benar anonim (tidak ada cara verifikasi siapa yang buka link), fitur ini **TIDAK BOLEH bocorin data privat/sensitif apapun** (constraint eksplisit dari user) - lihat daftar field di bawah.

- **Data model:** `trips.share_token` (varchar, nullable, unique) - kolom baru di `trips`, BUKAN tabel terpisah. Null = sharing belum aktif. Beda total dari `trip_viewers`/`viewer_invite_token` (Section 9) - tidak ada baris tersimpan soal siapa yang buka link ini, tidak ada akun yang terlibat sama sekali.
- **Generate/matikan link:** pemilik trip tap "Bagikan Itinerary" di layar detail trip -> `POST /api/trips/{id}/share-link` generate `share_token` kalau belum ada (idempotent - link yang sama terus dipakai sampai sengaja di-reset, bukan generate ulang tiap tap). Tap "Matikan Link"/"Reset Link" -> `DELETE /api/trips/{id}/share-link` -> `share_token` di-null-kan, link lama langsung mati buat siapapun yang masih pegang.
- **Endpoint publik, tanpa Sanctum sama sekali:** `GET /api/shared-itinerary/{share_token}` (sengaja beda path dari `GET /api/trips/shared` milik Trip Viewer di Section 9 - itu butuh login, arti beda total, jangan sampai ketuker) - satu-satunya endpoint di seluruh API yang benar-benar publik terhadap data sebuah trip milik user tertentu (beda dari `GET /api/places` yang publik tapi memang data umum katalog). Lookup langsung by `share_token`; kalau tidak ketemu (null/sudah di-reset), balikin 404 generik - jangan bocorin info "trip ini pernah ada tapi link-nya mati" vs "link ini memang tidak pernah valid".
- **Field yang DIBOLEHKAN muncul di response publik (whitelist ketat, bukan blacklist):** title trip, num_days, start_date, daftar itinerary per hari (nama tempat, alamat, foto, visit_order, estimated_visit_minutes), polyline_to_here per segmen (buat render rute kalau mau ditampilkan di peta).
- **Field yang WAJIB DIKECUALIKAN (no privacy leak):**
  - **`visited_at`/progres kunjungan live** - sama sekali tidak dikirim. Beda dari Trip Viewer (Section 9) yang memang didesain buat lihat progres live, fitur ini cuma buat lihat **rencana**, bukan status real-time. Lokasi GPS pemilik sendiri memang sudah tidak pernah sampai ke server sama sekali (Section 8) - tapi `visited_at` (kapan sebuah stop ditandai selesai) tetap dianggap data personal/status trip yang tidak layak dilihat orang anonim.
  - **Identitas pemilik** - nama, email, foto profil, atau field `users` apapun TIDAK ikut di response. Serializer publik ini query lewat `trips` langsung, tidak pernah include relasi `users`.
  - **`budget_total`** - dikecualikan by default, bukan cuma "tidak diminta" - link publik yang bocorin nominal anggaran orang ke siapapun yang pegang link bukan trade-off yang masuk akal buat manfaat fitur ini.
  - **Lokasi hotel custom pin presisi** - kalau `trips.has_own_hotel` pakai `hotel_lat`/`hotel_lng` (nama kolom disamakan dengan Section 4, 2026-10-10) (bukan hotel dari katalog `places`), default aman: sembunyikan koordinat presisi di respons publik, tampilkan label generik "Hotel" tanpa titik lat/lng. Hotel dari katalog `places` aman ditampilkan apa adanya karena memang lokasi publik.
  - **Data trip lain milik user yang sama** - endpoint ini scoped ketat ke SATU `share_token` -> SATU trip, tidak ada cara dari sini buat enumerasi/lihat trip lain milik pemilik yang sama.
- **Kenapa whitelist, bukan blacklist:** field baru yang ditambahkan ke `trips`/`itinerary_items` di masa depan defaultnya TIDAK muncul di response publik ini kecuali sengaja ditambahkan ke whitelist - lebih aman daripada blacklist yang berisiko kelupaan nge-exclude field sensitif baru begitu skema berkembang.
- **Tidak ada rate limiting/anti-scraping khusus didesain sekarang** - `share_token` cukup panjang & random (misal 32 karakter via `Str::random()`) buat sulit ditebak brute-force dalam skala proyek 1 semester; kalau nanti jadi masalah nyata, tambah throttle di route publik ini.
- **Cara bagikan:** tombol "Bagikan Itinerary" di layar detail trip pemilik -> link dikirim lewat share sheet OS (`share_plus`) ke WhatsApp/dll, atau tombol "salin link". Deep link `smarttrip://shared/{share_token}` buka app langsung ke layar itinerary read-only (Section 13) - **wajib install app**, tidak ada fallback web (keputusan sadar, proyek ini tidak punya frontend web publik).
- **Kenapa terpisah dari Trip Viewer, bukan digabung:** dua kebutuhan yang beda - ini buat "broadcast ke siapa saja, sekali lihat, tanpa akun" (megaphone), Trip Viewer buat "kasih akses spesifik ke orang tertentu, persisten, bisa dicabut per-orang, termasuk lihat progres live" (guest list). Menggabungkan keduanya jadi satu sistem otorisasi cuma bikin lebih rumit tanpa manfaat jelas buat kedua use case ini.

## 11. Weather Forecast & Swap Suggestions

Weather **tidak** ikut masuk sebagai kriteria ke-5 di TOPSIS/generate (Section 7) - forecast cuma reliable beberapa hari ke depan (Open-Meteo balikin sampai 16 hari, tapi akurasinya turun jauh setelah ~7 hari), sementara `start_date` trip bisa diisi berminggu-minggu ke depan saat generate pertama kali dijalankan. Jadi ini fitur **terpisah, muncul belakangan**, bukan bagian dari algoritma generate:

1. **Kapan forecast mulai ditampilkan:** begitu `trip.start_date` sudah dalam window ~7 hari dari hari ini (dicek client-side tiap kali layar itinerary/live map dibuka), Flutter panggil Open-Meteo langsung (Section 3 - tanpa API key, tanpa lewat backend) pakai koordinat hotel/titik awal trip sebagai proxy cuaca buat seluruh kota (Batam kecil, 1 titik cukup representatif, tidak perlu query per-stop).
2. **Notifikasi otomatis saat window terbuka:** selain dicek tiap layar itinerary/live map dibuka (langkah 1), begitu itinerary selesai di-generate, Flutter langsung menjadwalkan **local notification** (`flutter_local_notifications`, pola sama seperti reminder mulai hari di Section 2) buat `start_date - 7 hari` (jam tetap, misal 08:00 waktu device) - isinya ajakan buka app buat cek forecast trip yang mau dimulai, tap notifikasi langsung ke layar hasil itinerary. Ini murni jadwal lokal berbasis tanggal yang sudah diketahui saat generate, **tidak fetch Open-Meteo di background** - forecast beneran baru diambil saat layar itinerary/live map dibuka (langkah 1), bukan dari isi notifikasi. Kalau trip di-edit dan `num_days`/`start_date` berubah (regenerate penuh, Section 12), notifikasi lama dibatalkan dan dijadwalkan ulang ke `start_date` baru - sama seperti reminder mulai hari yang juga di-reschedule saat regenerate. Kalau `start_date` trip kurang dari 7 hari lagi saat pertama kali di-generate, notifikasi dijadwalkan langsung buat besok pagi (bukan di masa lalu).
3. **Tampilan:** forecast (ringkasan cuaca + probabilitas hujan) muncul di kartu tiap hari di layar hasil itinerary dan di live map, murni informasi.
4. **Saran swap:** kalau suatu hari punya minimal 1 stop dengan `places.is_outdoor = true` DAN forecast hari itu nunjukin kemungkinan hujan signifikan, kartu hari itu dapat badge/banner ("Prediksi hujan - mau ganti tempat outdoor?"). Tap badge langsung buka swap modal yang sudah ada (Section 7 langkah 7) buat stop outdoor tsb - **tidak ada regenerate/TOPSIS ulang otomatis**, user yang putuskan swap atau tidak.
5. **Kenapa client-side, bukan lewat backend:** Open-Meteo tidak butuh API key (Section 3), jadi tidak ada rahasia yang perlu dilindungi server - konsisten dengan alasan `google_maps_flutter`/`geolocator` dipanggil langsung dari mobile. Notifikasi window pun cuma jadwal lokal (langkah 2), bukan push server - tidak butuh Firebase Cloud Messaging atau endpoint backend baru buat fitur ini.

## 13. Mobile App Flow (Flutter)

0. Pilihan bahasa (ID/EN) - default ikut bahasa device, bisa diganti kapan saja lewat settings
1. Home (browse katalog tempat bisa tanpa login) -> tap "Buat Trip" -> kalau belum login, diarahkan ke Login/Register dulu (wajib, tidak ada opsi "lanjut sebagai guest"). Layar ini juga ada tombol "Masuk pakai Google" (`google_sign_in` Flutter package -> `POST /api/auth/google`) selain email/password.
1a. **Onboarding minat - gate berdasarkan kondisi, bukan event sekali jalan:** setiap kali app dibuka dengan sesi login aktif (bukan cuma tepat setelah Register - checked di app launch DAN tiap habis Login berhasil), cek `default_interest_category_ids` user. Kalau kosong, layar Pilih Minat (multi-select chip, wajib pilih minimal 1) muncul dan **memblokir** semua layar lain sampai terisi - hasilnya langsung `PUT /api/profile/preferences`. Kalau sudah ada isinya, langsung lanjut seperti biasa tanpa muncul apa-apa. **Ini otomatis nutup edge case user nutup app tepat setelah Register** (sebelum sempat isi minat) - tidak butuh flag/state "baru saja register" sama sekali, gate-nya murni cek kondisi "masih kosong atau tidak" tiap kali sesi mulai, jadi kalau ke-skip kemarin (app ditutup paksa), bakal ke-tangkep lagi pas dibuka lagi. Setelah keisi, lanjut ke tujuan awal (trip setup kalau trigger-nya dari "Buat Trip", atau Home kalau login biasa). Berlaku sama persis buat akun baru dari Google Sign-In - tidak butuh kode khusus, karena akun baru (dari jalur manapun) otomatis punya `default_interest_category_ids` kosong dan langsung ke-gate oleh pengecekan yang sama.
2. Trip setup: num_days, budget_total, start_date, daily start/end time (opsional, default ditampilkan), toggle "sudah punya hotel?"
3. Wishlist (opsional): katalog tempat gaya e-commerce (grid/list, filter kategori, infinite scroll) dengan tombol "+ wishlist" per kartu. Tempat yang tidak ada di katalog bisa ditambah manual: cari dulu, kalau tidak ketemu baru tap/drag pin di peta (`google_maps_flutter`) + nama bebas + **estimasi durasi kunjungan (menit, wajib diisi - revisi 2026-09-22, dipakai buat budget waktu hari di Section 7 langkah 6b karena pin custom tidak punya data ini dari katalog)** - tanpa Geocoding API.
4. Pilih minat (multi-select chip kategori) + slider preferensi (4 kriteria, 0-10) - dua langkah beda tujuan, lihat Section 7 langkah 3. Kalau `user_default_interest_category`/4 kolom `default_weight_*` sudah ada (dari Profil atau trip sebelumnya), layar ini pre-filled - user tinggal edit kalau mau beda buat trip ini. Ada toggle "simpan sebagai default" (opsional, tidak auto-overwrite diam-diam) buat update `user_default_interest_category`/4 kolom `default_weight_*` dari pilihan trip ini.
5. Kalau sudah punya hotel: cari di katalog (pola sama persis kayak wishlist di atas - search dulu, pin manual kalau tidak ketemu). Kalau belum: tampilkan top-3 pilihan hotel hasil TOPSIS.
6. Loading -> hasil itinerary (otomatis tersimpan ke akun, tidak ada langkah "simpan" terpisah): kartu per hari, tiap tempat ada badge source (wishlist/recommended). Reminder "mulai hari ini" otomatis terjadwal (local notification) untuk tiap hari di itinerary.
7. Menu "..." per item -> swap (alternatif ranking atau cari manual)
8. Tombol "Buka Peta" per hari -> live map (lihat Section 8): marker hotel, lokasi user saat ini, pin bernomor per stop, polyline abu-abu/biru sesuai status kunjungan; geofencing otomatis aktif selama layar ini/trip berjalan. Notif "sudah dekat stop berikutnya" muncul saat geofence entry terpicu.
9. List trip tersimpan -> buka lagi, edit lewat `PATCH /api/trips/{id}` (itinerary dibuang kalau num_days/budget/jam harian berubah, lalu generate penuh lagi; ganti hotel lewat `POST /api/trips/{id}/hotel` lalu generate; partial swap kalau cuma ganti 1 tempat), hapus, tambah review in-app setelah kunjungan
9a. **Layar "Bagikan Trip" (baru, revisi 2026-09-23 - lihat Section 9):** dari detail trip milik sendiri, tombol "Bagikan" buka layar dengan **dua bagian terpisah, jangan ketuker:**
   - **Undang Viewer** (butuh akun/login, akses persisten): cari user terdaftar by email -> tap tambah, langsung jadi viewer. Atau tombol "Bagikan Link Undangan" -> generate/ambil `viewer_invite_token`, kirim lewat share sheet OS. Kedua jalur nampil di daftar viewer yang sama + tombol cabut akses per viewer (Section 9).

Tombol "Matikan Link" buat reset (Section 10). **Ini bukan bagian dari daftar viewer** - tidak ada yang tercatat siapa buka link ini.
9b. **Tab "Dibagikan ke Saya" (baru, revisi 2026-09-23):** tab terpisah dari "Trip Saya", isinya list trip yang dibagikan orang lain ke akun ini sebagai viewer (`GET /api/trips/shared`) - baik yang diundang lewat email maupun lewat link undangan, keduanya nongol di sini sama saja. Tap buka detail trip yang sama persis (itinerary, peta live, status hari) tapi **read-only** - menu "..." swap, tombol generate ulang, hapus, dan tandai kunjungan manual semuanya disembunyikan/dinonaktifkan di layar ini.
9c. **Buka link undangan viewer (`smarttrip://invite/{token}`):** kalau belum login, app arahkan ke Login/Register dulu (intent link disimpan sementara), begitu berhasil auth langsung `POST /api/trips/join-viewer/{viewer_invite_token}` lalu masuk ke trip (masuk daftar "Dibagikan ke Saya"). Kalau sudah login, langsung join tanpa jeda layar tambahan.
9d. **Buka link Share Itinerary (`smarttrip://shared/{token}`):** langsung buka layar itinerary read-only **tanpa login sama sekali** (Section 10) - tidak masuk tab manapun, tidak tersimpan di akun, murni tampilan sekali lihat dari `GET /api/shared-itinerary/{share_token}`.
10. Tab Profil - edit `user_default_interest_category` + 4 kolom `default_weight_*` langsung (di luar alur bikin trip), lewat `GET/PUT /api/profile/preferences`

Alur di atas berlaku buat semua user aplikasi Flutter. Admin tidak pernah buka app ini - lihat Section 14 buat alur admin (web terpisah).

- **Login admin** (revisi 2026-10-14) - `/` langsung diarahkan ke `/admin/login`; halaman login dan **Lupa Kata Sandi** (`/admin/forgot-password`) pakai Tailwind lewat Vite (deploy menjalankan `npm ci && npm run build`). Lupa Kata Sandi memakai `Password::sendResetLink` yang sama dengan API mobile, balasannya sama apa pun emailnya (tidak bisa dipakai mengecek email terdaftar), dibatasi 5 permintaan/menit.
- **Review candidate tempat** (Section 3) - tombol trigger discovery per area/kategori, list `place_candidates` (filter per search_area/status, pakai DataTables/table biasa), approve (promosikan + fetch detail lengkap + AI enrichment) atau reject - bisa satu-satu atau bulk-select
- Status sync terakhir (kapan discovery/enrichment terakhir jalan, berapa candidate pending, indikator pemakaian kuota Enterprise)
- Dashboard analitik (chart/kartu ringkas) - tempat paling di-wishlist, rata-rata rating in-app, volume trip, **daftar tempat yang belum ada estimated_cost_idr**, **daftar tempat yang `category_tags_reviewed`-nya masih false**

**Kenapa balik ke web:** admin panel web (Blade + Bootstrap, sesuai konvensi tim di project Laravel lain) lebih cepat dibangun buat layar berat-data kayak list+filter place_candidates dan dashboard chart, dibanding native Flutter - dan sekarang admin memang tidak perlu install app mobile sama sekali buat kerja kurasi data.

## 15. Testing Approach

- Backend: unit test untuk bagian matematis murni (normalisasi bobot, scoring TOPSIS, Haversine, K-Means clustering, blend rating Bayesian) karena deterministik dan gampang diverifikasi terhadap input yang sudah diketahui hasilnya - bagian ini juga paling penting untuk dipertanggungjawabkan metodenya.
- Feature test untuk endpoint API (alur create trip -> generate -> swap -> visit) DAN feature test buat route admin web (CRUD places/categories, approve/reject candidate).
- Feature test khusus buat otorisasi trip viewer (revisi 2026-09-23, Section 9): viewer bisa baca (`GET /api/trips/{id}` dst), tapi setiap endpoint tulis (swap/generate/hapus/visit/weights) HARUS ditolak (403) buat viewer yang bukan pemilik - ini titik paling rawan bug kalau lupa cek di satu endpoint saja.
- **Feature test khusus buat whitelist field `GET /api/shared-itinerary/{share_token}` (revisi 2026-09-23, Section 10) - wajib, bukan opsional:** assert response TIDAK PERNAH mengandung `visited_at`, field apapun dari relasi `users` (nama/email pemilik), dan `budget_total`, bahkan kalau field baru ditambahkan ke `trips`/`itinerary_items` di masa depan. Test ini yang menjaga kontrak "no privacy leak" tetap benar seiring skema berkembang, bukan cuma review manual sekali waktu fitur ini dibuat.
- Flutter: widget test untuk layar input slider/wishlist, QA manual untuk alur penuh termasuk geofencing (auto-generate output & lokasi GPS tidak praktis diasersi persis lewat widget test).

## 16. Out of Scope (semester ini)

- Laporan akademik (di luar dokumen ini per instruksi user)
- Scraping platform lain (TripAdvisor/Traveloka/Tiket.com) - hanya Google Places sebagai sumber data eksternal
- True AHP pairwise comparison - dipakai direct-rating slider yang lebih simpel untuk UX mobile
- **Co-editing/kolaborasi trip** - direvisi 2026-09-23: read-only sharing (satu pemilik, viewer lain cuma bisa lihat) SUDAH masuk scope, lihat Section 9. Yang masih di luar scope adalah **multi-editor** (lebih dari satu orang yang bisa ubah trip yang sama), komentar/diskusi in-app, dan real-time sync/conflict resolution antar editor - itu semua butuh model preferensi multi-user yang lebih kompleks (skor TOPSIS trip cuma didesain buat 1 set bobot pemilik, bukan gabungan preferensi banyak orang)
- Re-routing otomatis kalau user menyimpang dari rute (out of order visit tetap dicatat per-stop, tapi tidak ada logika "hitung ulang rute optimal dari posisi user sekarang")
- Publish ke Play Store/App Store (kalau nanti perlu, siapkan privacy policy + justifikasi background location permission dulu)
- Booking/reservasi/pembayaran (tiket masuk, kamar hotel, meja restoran) - app murni rekomendasi & perencanaan, bukan transaksi
- Ganti hotel di tengah trip (1 hotel = 1 titik awal/akhir buat seluruh trip, wajar untuk kota sekecil Batam)
- Batas num_days disarankan max 7 hari (bukan hard rule teknis, tapi realistis mengingat pool awal cuma ~300-500 tempat kurasi - bisa direvisit setelah lihat kepadatan data asli Batam pasca sync pertama)
- Multi-kota - skema Batam-only, tidak ada field `city` di manapun (places, trips, area list Discovery semua hardcode buat Batam). Kalau nanti mau ekspansi ke kota lain, butuh migration + refactor Discovery, bukan cuma config baru - keputusan sadar buat menghindari kerja di muka buat kemungkinan yang belum pasti kejadian semester ini.
- Jam operasional per-hari berbeda dalam 1 trip (misal hari kedatangan mulai lebih siang, hari kepulangan selesai lebih awal) - `daily_start_time`/`daily_end_time` tetap 1 nilai berlaku semua hari; kalau ada hari yang perlu jam beda, user swap manual tempat yang kepepet waktu
